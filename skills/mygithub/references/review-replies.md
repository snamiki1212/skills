# コードレビューコメントへの返信

「コメントを打ち返して」「レビューコメントに対応して」と依頼されたら、対象 PR の未解決・解決済みを問わず、その依頼が指すコードレビューコメントを確認する。
まず、各コメントが指すコード、周辺の実装、テスト、既存の議論を調べる。
コメント文だけから結論を決めない。

## 対応の流れ

各コメントについて、次の順で進める。

1. 指摘が正しいか、現在の実装に対して必要かを判断する。
2. 指摘が生じた理由を調べ、同種の問題を生む設計・テスト・レビュー手順の欠落など、構造的な問題があるかを判断する。
3. 構造的な問題への対策が現在の PR の目的と範囲に収まるなら、個別の修正と併せて実装し、必要な検証を行い、修正コミットを PR に積む。
4. 対策が現在の PR の範囲を超えるなら、個別の修正とは分けて別 PR を作成し、その PR で対応する。
5. コミットを確認してから、そのコメントに返信する。
6. 対応が不要なら、変更を加えず、その理由を添えて返信する。

構造的な問題がない、または対策を追加しないと判断した場合も、その理由を確認する。
現在の PR に関係のない変更を混ぜてスコープを広げない。

レビューコメントへの返信だけを目的に、スレッドを `resolve` してはならない。
`resolve` は、変更と返信を確認した人間が行う判断として残す。

修正が他のコメントにも影響するなら、関係する各スレッドでその関係を説明する。
一つの返信で別のコメントを曖昧に閉じない。

## 返信の書式

返信は、冒頭で結論を示す。
結論は次のどちらかにする。

```text
対応: あり
```

```text
対応: なし
```

続けて、判断の背景を箇条書きで書く。
`対応: あり` では、何を直したか、構造的な問題への対策、修正コミット、検証結果を含める。
対策を別 PR に分けた場合は、その PR へのリンクと切り分けた理由も含める。
`対応: なし` では、なぜ変更しないのかを具体的に説明する。

例。

```markdown
対応: あり

- `parseConfig` が空文字列を許容しており、この経路では意図しない既定値にフォールバックしていました。
- 空文字列をエラーにする検証を追加しました。
- 同種の入力不備を境界で検出できていなかったため、設定値を検証する共通処理にも空文字列の検証を追加しました。
- 修正は abc1234 に含め、関連テストを実行しました。
```

```markdown
対応: なし

- この分岐は `mode: legacy` の互換経路だけから到達します。
- 現行の呼び出し側では値を正規化しているため、指摘された `undefined` は渡りません。
- ここで既定値を追加すると、互換経路の入力不備を検出できなくなります。
```

AI を介して GitHub に返信を投稿するときは、末尾に実行主体を追記する。
使用した製品名とモデルの完全な名称を分かる範囲で明記する。
モデル名は系列名へ丸めず、バージョン・バリアント・接尾辞を省略しない。

```text
Posted by Codex (GPT-5.6 Terra)
```

モデル名が分からない場合も製品名は省略しない。
例: `Posted by Claude`。
