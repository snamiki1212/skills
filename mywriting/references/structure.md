# 複数ファイル構成の規範（単一責任・参照・抽象レベル）

一つの文書群を複数のファイルに分けて書くときの規範。ファイルを新しく分けるとき、既存の分割を再編するときに従う。

## ファイルの単一責任

ソフトウェアにおける単一責任の原則を、文書のファイル分割にも適用する。一つの事柄の説明は、一つのファイルだけが持つ。

- ある事柄を変更するとき、直すファイルが一つで済む構造にする。同じ説明を複数のファイルに置くと、一箇所を変えたときに他の箇所が古いまま残る。
- 同じ説明が複数のファイルに要りそうになったら、どちらのファイルの責務かを決めて片方に寄せる。どちらの責務でもないなら、その事柄を担う置き場所（新しいファイル、上位の入口ファイル）を作る。
- 同列に並ぶファイルどうしは、互いを参照せず、それぞれ自分の責務だけで完結させる。同列のファイルが互いを見合う・循環して参照する構造は、切り分けの軸が責務に沿っていない兆候である。ある内容を書くのに同列ファイルへの参照が要るなら、その内容の置き場所が違う。

## 参照の書き方

参照先にしかない情報を、呼び出し元に書かない。

- 上位のファイルから下位のファイルの内容を指すときは、参照とだけ書く（「詳細は `references/foo.md` を参照」）。
- 参照先の内容の要約・抜粋・言い換えを呼び出し元に添えない。参照先を変えたとき、呼び出し元に残った要約が古くなり、二重管理になる。
- 呼び出し元に書いてよいのは、読者がその参照を辿るかどうかを判断するための最小限の情報（何についてのファイルか）だけである。
- 参照先は文書に限らない。処理の実体が一つのファイル（例: Makefile）に集約されているとき、その処理内容を README など他のドキュメントに列挙して二重管理しない。ドキュメントには入口となるコマンドと参照先（例: `make help`）だけを書き、詳細は集約先に隠蔽する。

## ファイル構造の SLAP

SLAP（Single Level of Abstraction Principle）をファイル構造にも適用する。同じ階層に並ぶファイル・フォルダは、抽象レベルを揃える。

- 同列に並ぶ単位の粒度を揃える。悪い例：`references/` 配下に `parser.md`・`linter.md`・`formatter.md` が並んでいて、`parser.md` だけが肥大化したのでフォルダ `parser/` に分割し、残りはファイルのまま置く。一つだけフォルダにすると、同列の並びに抽象レベルの段差ができる。良い例：一つをフォルダにするなら、`linter/`・`formatter/` も同じようにフォルダへ揃える。
- 揃えるためだけの分割が過剰に感じられるなら、それは分割が早すぎた兆候である。フォルダ化する前に、肥大化した一つを 1 ファイルのまま保てないかを先に検討する。
